# ChainHash adjacent pairing: EXT kernels on Apple M2 Pro

Best 256-byte definition: **chainhash-ext-k3-256 = 19.98 B/cycle**, 0.883× the strided control. Best 1 KB definition: **chainhash-ext-k1-1024 = 17.45 B/cycle**, 0.926× its strided control.

**No adjacent kernel reaches 95% of its strided control.** These measured implementations favor strided pairing on this M2; retaining the adjacent definition is an author-level portability/function choice, not a demonstrated speed win here.

## Measured load/EXT throughput

| Independent L1 loop | Median ns / group |
|---|---:|
| ld2 | 0.2992 |
| ldp | 0.2117 |
| ldp_ext | 0.2116 |
| ext_only | 0.0746 |

LD2 took **1.41×** the time of LDP and **1.41×** the time of LDP+EXT per 32-byte group. The standalone independent EXT loop measured 0.0746 ns/instruction. These are reciprocal throughput costs including amortized loop overhead, **not latency measurements**.

The microbenchmark uses eight independent groups per iteration, 20 million iterations, seven samples per mode, a hot aligned L1 address and no PMULL. LD2 and LDP each fetch 32 bytes; LDP+EXT additionally forms the adjacent cross-lane vector. EXT-only reads independent fixed source registers. Every instruction remains in volatile asm; the actual disassembly is retained. These measurements test the cost of choosing a de-interleaving load instead of a regular load plus vector shuffle. They do not count micro-ops or identify execution ports, so a precise micro-op decomposition is not claimed. The hash results additionally include recurrence, message streaming and register allocation. LDP+EXT and LDP alone measured essentially the same throughput, consistent with the EXT work overlapping the loads. The 1.41× load-only ratio supports an LD2 throughput penalty, but does not fully explain the previous roughly 2× whole-hash gap.

## Implementation and correctness

`CHAINHASH_ARM_KERNEL=1` selects contiguous message/key LDP plus EXT. With X=[x0,x1], Y=[y0,y1], T=EXT(X,Y,8)=[x1,y0], PMULL(X,T) forms x0*x1 and PMULL2(Y,T) forms y1*y0. Carry-less multiplication is commutative, so the second product is the required y0*y1.

`CHAINHASH_ARM_KERNEL=2` prepares [k0,k2],[k1,k3] during key construction and pins its key loads to LDP. Its runtime key stores canonical words plus a PH cache: 584 bytes for B=256 and 2120 bytes for B=1024. Serialized key input remains 328/1096 bytes with the same entropy and function. Use the ARM key constructors; changing `.words` afterwards requires rebuilding the prepared key. The portable wrapper consumes the canonical words. K1/K3 retain the original exact key structure.

`CHAINHASH_ARM_KERNEL=3` uses an unrolled 256-byte PH asm block with 16 simultaneous key-vector inputs, three scratch vectors and two accumulators. Explicit memory operands describe the input region without a blanket memory clobber, allowing key loads to be hoisted. The actual object confirms that key registers persist across repeated blocks, including batch-4, without spills.

Low products and recurrence state are pinned to PMULL/lane 0; high products and reduction folds use PMULL2. The recurrence state never makes a SIMD/GPR round trip in the bulk loops. The coefficient-side EXT outside PH and final scalar return are intentional. Two dependent PMULL2 folds reduce modulo X^64+X^4+X^3+X+1.

Batching changes evaluation order only. The 256-byte batch-4 path composes four affine maps in a balanced tree before applying the incoming state. It has seven field multiplications per four blocks versus four for k=1. The final length-injected block is peeled in both cases. Batch-2/8 APIs remain available and are identity-tested; only k=1/4 are timed here.

For **each of the five supported kernel/definition combinations**, 20,535 input cases passed against both the portable reference and an independent SPEC-derived bit-serial oracle: 12,000 fresh random inputs/keys with lengths 0..4096 and offsets 0..63, every short length, guard-page tails, 16 long lengths through 1 MiB, block/batch boundaries, adversarial keys/data and null empty input. All batch entry points were compared. Canonical key constructors, 128 reduction basis polynomials and 10,000 random affine compositions also passed. Returned-word identity implies byte-identical canonical LE serialization.

A separate UBSan suite passed 8,194 guarded short cases per combination plus long inputs through 1 MiB. Native C99 and forced-portable smoke tests passed for all combinations. No ASan result is claimed. Full identity and guard verification ran serially locally and finished before timing. Native/forced-portable C99 smoke checks ran again after the post-timing default-selector adjustment.

## Evidence and reproduction

Actual benchmark objects, including batch-4, were disassembled with `xcrun llvm-objdump -d`. `evidence/actual-object-loop-audit.json` records loop address ranges and opcode counts. Its control-flow check excludes backward branches that merely join tail code after a return. **Every actual bulk loop has zero SIMD stack accesses and zero SIMD/GPR transfers.** Tail-copy/ABI saves outside those loops are allowed and retained in the disassembly.

Benchmark binary SHA-256: `592010540dcc66e2f77dfd17e580f199286e4fdff9f85dc10b64b0420a654a4d`. The scratch tree is a copy of the previous lane’s tree. Strided controls and SpeedTest.cpp are byte-identical to that tree; compiler commands and provenance are in `evidence/provenance.json`. No timing conversion or benchmark loops were changed. All benchmark adapters select kernels explicitly. After timing, only the header’s default selector and diagnostics/comments changed; the measured header is retained as `evidence/chainhash_arm.measured.h`, and all measured kernel bodies are unchanged.

Each accepted run started with no SMHasher process and one-minute load below 4.5; accepted starting loads range 3.5259–4.4966. The runner checks every five seconds during each run and rejects observed overlap independently of measured speed. Excluded attempts: 1. Raw samples, hashes, timestamps, load histories and outliers are retained in `speeds_m2_adjacent_ext.json` and `evidence/speeds/`. Background system activity between checks cannot be ruled out.

```sh
python3 run_tests.py
cmake -S smhasher3 -B build -DCMAKE_BUILD_TYPE=Release \
  -DENDIAN_DETECT_BUILDTIME=OFF -DDETECTED_LITTLE_ENDIAN=ON \
  '-DCMAKE_CXX_FLAGS=-Xclang -target-feature -Xclang +aes' \
  -DCMAKE_OSX_SYSROOT=/Library/Developer/CommandLineTools/SDKs/MacOSX.sdk \
  -DCMAKE_EXPORT_COMPILE_COMMANDS=ON \
  -DOPENSSL_ROOT_DIR=/opt/homebrew/opt/openssl@3
cmake --build build --target SMHasher3 -j2
python3 audit_objects.py
python3 run_speeds.py  # resumes same binary; rerun after an overlap exclusion
clang++ -std=c++11 -O3 -march=native tests/load_micro.cpp -o evidence/load_micro
python3 run_micro.py
python3 make_report.py
```

Use a fresh `evidence/speeds/` directory for a new binary/campaign. The default block definition remains 1024 bytes using K1. On Apple Silicon macOS or SHA3-enabled AArch64, the 256-byte definition defaults to K3 (K1 on other targets). Apple Clang’s native recipe omits the SHA3 feature macro despite supporting/emitting EOR3, so the selector recognizes Apple Silicon macOS explicitly. Select 256 bytes with `CHAINHASH_X86_BLOCK_BYTES=256`. Kernel choice and batching never select a different function within that definition.
